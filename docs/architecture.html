GlowRoot · system architecture · as built, July 2026

Two Next.js apps, five shared packages,
and one JSON file they both trust.

GlowRoot is a Turborepo + pnpm monorepo. A customer storefront and an internal admin panel run as separate Next.js 14 processes that share types, UI and a single data-access package. There is no API server and no database yet — the two processes meet at JSON files on disk at the repo root, which is exactly the seam a real backend replaces.

.glowroot-orders.json

Read-modify-write on every change. Storefront appends at checkout, admin flips status and appends to history. Seeded from orders.ts on first run.

.glowroot-users.json

Accounts keyed by lowercased email — the same key orders carry, so identity needs no join. Passwords stored as salted PBKDF2-SHA256, 120k iterations.

The delivery map: one record per pincode (area, city, lead time, COD, paused) plus the nationwide switch. Admin Locations writes it; the storefront reads it on every page load for the serviceability hint and the hard checkout check.

The order path

The one flow that crosses every layer, in the order it actually runs. Steps 1–4 can all abort before anything is written to disk.

  1. Account gate isRegisteredUser(email) — the action is a public endpoint, so this holds even if the UI is bypassed. It proves the email has an account, not that the caller is that person.
  2. Hard serviceability check isServiceable(pincode) — the same predicate the header banner uses as a soft hint while browsing. Currently short-circuited by acceptAllPincodes = true.
  3. Price the order One-time: sum of qty × priceINR. Subscription: the plan's pricing[cycle] price, with items left un-itemised.
  4. Charge charge() runs before any write, so a decline leaves nothing behind. Cash on delivery returns pending rather than paid; card and UPI keep only a masked hint.
  5. Persist the order addOrder → appendOrder unshifts onto .glowroot-orders.json. Status opens at confirmed when paid, pending for COD, with the first history event stamped.
  6. Remember the customer saveCustomerProfile upserts name, phone, address and pincode into .glowroot-users.json — so the next checkout prefills, and a guest can claim their history later by signing up with the same email.
  7. Admin picks it up The order appears on :3001 on next render. changeStatus appends to history and revalidates /orders, /orders/[id] and /.
  8. Customer reads it back /account/orders for signed-in customers, /track for guests — which requires order ID and the email it was placed with, since an ID alone is guessable.

What the diagram implies

Consequences of the shape above that are worth stating outright, in both directions.

Trust boundary

Email is supplied by the client

With the session in localStorage there is nothing server-side to read an identity from, so fetchMyOrders(email) and placeOrder take the email as an argument. Anyone can call those actions with someone else's address. /track is the exception — it demands the order ID too.

Concurrency

Two writers, one file, no lock

Both processes do read → mutate → whole-file write. A storefront checkout landing at the same moment as an admin status change can lose one of the two. Fine for a prototype; it's the first thing a real datastore fixes.

Deployment

Shared disk is a hard requirement

The two apps only agree because they resolve the same repo-root path. Deploy them to separate hosts or a read-only filesystem and they silently stop seeing each other's data.

Holding up well

The accessor boundary is real

No page imports a raw data array, and every accessor is already async. The one deliberate exception — @glowroot/data/serviceability, a pure predicate imported by a client component — is a separate export precisely so fs never follows it into the bundle.

Holding up well

Secrets don't cross the wire

User never leaves the server; toPublic() strips the password hash before any record reaches a client, and payment instruments are masked down to a hint before being stored.

Holding up well

Orders map to inventory

Each Product carries a recipe of raw Materials, so a bottle sold on the storefront is traceable to the produce the admin tracks — the join that makes the two apps one system rather than two.
