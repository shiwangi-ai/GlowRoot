GlowRoot · component architecture companion to architecture.html (runtime view)

Thirty-six components, two context providers,
and one boundary that matters.

Composition here is page-driven: route pages are the only real composers, and everything below them is a leaf or a near-leaf. Interactivity is pushed as far down the tree as it will go — a server-rendered section will render a single client button rather than becoming a client component itself. That one habit explains almost every shape on this page.

How data and events cross the boundary

Three moves, and no fourth. There is no client-side fetching anywhere in the storefront — every island gets its data as props or calls a server action.

Downward · props

Server page fetches, then hands over

A route page awaits @glowroot/data accessors and passes plain serializable objects down — Product[], Plan[], deliverySlots. The island never learns where they came from.

Sideways · context

Cross-cutting state comes from context

Cart, pincode and session skip the prop chain entirely: 15 components call useStore() or useAuth() directly. That's why SiteHeader can show a live cart count without the page knowing a cart exists.

Upward · server actions

Islands call back into the server

CheckoutClient → placeOrder. AuthForm → signIn / signUp. AccountOrders and TrackOrderForm → fetchMyOrders / trackOrder. Six of the seven actions are invoked from exactly one component.

What the tree shows

Six things that fall out of the composition graph rather than the runtime shape.

Dead code

CartDrawer is never rendered

136 lines, imports useStore and Button, and no file in either app references it — CartIsland took over the job. It still type-checks and still ships in the graph, so it reads as live when it isn't.

Boundary is wider than it looks

Two components are client-side without saying so

OrderDetailCard and OrderTimeline carry no "use client", but their only parents are AccountOrderDetail and TrackOrderForm — both clients. React pulls them into the client bundle regardless, so the directive count of 22 understates the real boundary by two.

Concentration

CheckoutClient is the outlier

507 lines — 43% larger than the next component, and it holds the address form, field validation, delivery-slot choice, payment method UI, the error states and the placeOrder call. It's the one component where a split would pay for itself.

Holding up well

Islands are pushed to the leaves

Six of the nine home-page sections are server components that render one small client child. The pattern is consistent enough to be a rule: a section becomes an island only when the whole section is interactive (PlanGrid, ProductCarousel).

Holding up well

Two entry points, one subtree

/account/orders/[id] and /track reach the same OrderDetailCard → OrderTimeline pair through different doors — one with a session, one with an order ID plus email. The display logic wasn't duplicated for the guest path.

Holding up well

Flat, not deep

The longest chain is eight nodes and most branches are three. No component imports another through the @/ alias — siblings use relative paths, which keeps the graph legible and makes accidental cycles obvious.
