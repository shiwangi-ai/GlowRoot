GlowRoot · request flow & technology decisions for review · July 2026

Every screen is one of three kinds of request.
Only two of them reach the server.

This document walks a real user request down through the layers, shows exactly where an order goes today, and states why the stack is Next.js rather than a plain React app. The decisions quoted here are the ones recorded in docs/frontend.md and docs/customer-journey.md before the build started — not reasons assembled afterwards.

“How does a user place an order with no backend?”

There is server-side code — it just isn't a separate service. Next.js runs a Node server, and the order-placing function executes there, never in the browser. What the project doesn't have yet is a database and a standalone API. Orders are appended to a JSON file at the repository root, which both apps read. That was the plan's Phase 2/3 target; a real database is Phase 4.

→ Figure 4
“Why Next.js and not plain React?”

Three requirements decided it: the storefront is a public marketing asset that must be indexable and fast on first paint; the admin panel is data-heavy and better rendered on the server; and a two-person-scale project should not have to build and version its own API tier. Next.js answers all three. A plain React SPA answers none of them without extra services.

→ Figures 5 and 6
“What does this cost us?”

Two real constraints before production: the two apps only see the same orders because they share a filesystem, and the JSON file has no write-locking. Both are fixed by the same Phase 4 change — swapping one package's internals for a database. Nothing above that package has to change.

Figure 1

The three kinds of request

This is the whole mental model. Every click in the app is one of these three, and knowing which one it is tells you exactly how far down the layers it travels.

Type A · page view

Server renders, browser paints

Opening any URL — home, a product, the plans page, an admin table.

1 browser asks for a URL 2 server matches the folder 3 server reads the data 4 server returns finished HTML 5 browser paints, then wakes the buttons
Round trip · content arrives complete
Type B · interaction

Never leaves the browser

Add to cart, change quantity, open the mega-menu, set a pincode, toggle weekly/monthly.

1 click handled in the browser 2 shared cart state updates 3 saved to browser storage 4 UI re-renders instantly
No server contact at all
Type C · mutation

Server action round trip

Place an order, log in, sign up, look up an order, change an order's status in admin.

1 browser calls a server function 2 server validates and acts 3 server writes to disk 4 result returns to the browser
Round trip · no REST endpoint involved
Why this split matters commercially

Type B is the reason the site feels instant while shopping — the entire browsing and cart experience costs the server nothing. Type A is the reason a product page can be found on Google, because the page's text exists in the very first response rather than appearing after JavaScript runs. Type C is the only path that can change stored data, which makes it the only path that needs validating — and it's validated on the server, where a customer can't bypass it.

Type A in full: opening a product page

A customer clicks Summer Crush. Here is every layer that request passes through, in order, with where the code lives.

  1. browserRequest goes out
    GET /products/summer-crush to the storefront process on port 3000. No JavaScript needed yet — this works with scripts disabled.
  2. server · routingThe folder path is the route
    Next matches the URL to app/products/[slug]/page.tsx and hands it slug = "summer-crush". There is no route table to maintain — see figure 6.
  3. server · layoutThe shared shell wraps it
    app/layout.tsx supplies the header, footer, cart island and the two state providers to every page automatically. Nothing is repeated per route.
  4. server · renderThe page runs on the server
    It awaits three data calls — getProductBySlug, getProducts, getMaterials — and builds the finished markup. This code never ships to the browser, so the customer's device does none of this work.
  5. data layerOne package answers every question
    @glowroot/data is the only door to data in the whole system. Today the catalogue lives in TypeScript files it reads in-process; tomorrow the same call reaches a database. The page can't tell the difference.
  6. server · responseComplete HTML goes back
    The customer's first paint contains the real product name, price, ingredients and image — which is what makes the page indexable and fast, the reason recorded in customer-journey.md for not gating the catalogue behind a pincode.
  7. browserOnly the interactive parts wake up
    Just one component on this page ships JavaScript: the Add to order button. Across the whole codebase, 12 of 36 components never reach the browser at all — detailed in component-architecture.html.

Type B in full: adding to the cart

Worth showing because it explains a question that often comes up — how the cart survives a page reload when there's no backend storing it.

  1. browserThe button is clicked
    Handled entirely in the page already loaded. No request leaves the device.
  2. browser · shared stateThe cart updates in one place
    A single shared cart holds every line item. That's why the header count, the floating cart bar and the checkout summary all agree without talking to each other.
  3. browser · storageWritten to the browser's own storage
    Under the key glowroot.cart. This is what survives a reload — the cart is saved on the customer's device, not on our server. Consequence: it does not follow them to a second device, and clearing browser data clears the cart.
  4. browserThe bottle flies to the cart
    The animation requested in key-improvements.md item 4. Pure browser work — no latency, so it can be tuned freely.
Figure 4

Type C in full: how an order is placed today

The question this document was written for. Below, exactly what happens between pressing Place order and the order appearing in the admin panel.

First, a correction worth making

“No backend” isn't quite the situation. Next.js is the backend: it runs a Node server process, and placeOrder executes there — the browser only sends arguments and receives a result, exactly like calling an API. What's genuinely absent is a database and a separate API service. Server-side validation, pricing and persistence all exist today; they just persist to a file instead of Postgres. This was deliberate: frontend.md logs the data decision as “mock / local data — design the shapes first; add a real DB in a later phase.”

  1. browserThe checkout form calls a server function
    The customer's name, address, pincode, delivery date and slot, cart contents and payment choice are passed to placeOrder. No URL is constructed, no fetch is written — the call looks like an ordinary function call in the code.
  2. server · gate 1Does this email have an account?
    Checked on the server, so it holds even if someone bypasses the form. Current limitation: it proves the email belongs to a registered account, not that the caller is that person — real sessions are Phase 4.
  3. server · gate 2Can we deliver to this pincode?
    The hard check the UX contract requires before money changes hands. Currently switched off by an override flag that accepts any valid 6-digit pincode, so orders can be placed anywhere during the demo.
  4. server · pricingThe total is calculated server-side
    One-time orders sum quantity × price; subscriptions take the plan's price for the chosen cycle. Deliberately not trusted from the browser, where it could be edited.
  5. server · paymentThe mock gateway runs
    Validates the UPI ID or card number, pauses ~900 ms so the “contacting your bank” state is real, and returns a payment record already shaped the way a live provider would return one. Cash on delivery comes back pending rather than paid. Critically, this runs before anything is saved — a decline leaves no order behind.
  6. diskThe order is appended to a file
    .glowroot-orders.json at the repository root. The order gets an ID like GR-4821, opens at confirmed when paid or pending for cash on delivery, and starts a status history the customer's tracking page later reads.
  7. diskThe customer's details are remembered
    Saved into .glowroot-users.json so the next checkout prefills. A guest who never set a password still gets a record, and can claim their whole order history later by signing up with the same email.
  8. browserConfirmation
    The order ID comes back and the customer lands on the success page with delivery date, slot, items and total.
  9. admin · port 3001Operations sees it
    The second app reads the same file, so the order is on the orders list and counted in the dashboard KPIs on its next render. Staff change the status; that appends to the order's history.
  10. browserThe customer tracks it
    Signed in, via their account's order list. As a guest, via the public tracking page — which requires the order ID and the email it was placed with, because an order ID alone is guessable.

Why a file rather than browser storage

The original plan set a lower bar for this phase — “you can place an order (stored in memory/localStorage)”. The build went further to a shared file because Phase 3 required that an order placed in the storefront shows up in admin, and browser storage can't do that: the admin panel is a different app that never sees the customer's browser. One file at the repository root is the smallest thing both processes can agree on.

Why file-based routing, concretely

The same two product routes, expressed both ways. This is the difference that shows up daily.

React Router · a config to maintain 
// router.tsx — every route listed by hand
createBrowserRouter([
  { path: "/",                element: <Home/> },
  { path: "/products",        element: <List/> },
  { path: "/products/:slug",  element: <Detail/> },
  … 17 more, kept in sync manually
])

// Detail.tsx — data is the component's problem
const [product, setProduct] = useState(null)
useEffect(() => {
  fetch(`/api/products/${slug}`)   // ← an API
                                        //   you must build
    .then(r => r.json()).then(setProduct)
}, [slug])
if (!product) return <Spinner/>

Three things to keep aligned: the URL, the config entry, and the component. Plus an API endpoint and a loading state for every screen.

Next.js · the folder is the route 
// no router file exists
app/
├── page.tsx                  → /
├── products/
│   ├── page.tsx              → /products
│   └── [slug]/page.tsx       → /products/summer-crush
└── layout.tsx                → wraps all of them

// [slug]/page.tsx — data is fetched before render
const product = await getProductBySlug(slug)
if (!product) notFound()
return <article>…</article>

// no fetch, no endpoint, no spinner, no useState

Creating the file creates the route. The page can't render before its data exists, so the loading state isn't needed — and the data call never leaves the server.

The practical upshot

Both readings of “why routing this way” land in the same place. File-based over a route config: 20 routes and no list to maintain, so a URL and its page cannot drift apart. Server routing over a browser-only router: each URL is a real server response, so product pages are shareable, indexable and quick on first load — which the UX contract requires of a public storefront.

What the current approach costs

Stated plainly, so the trade-offs are on the record alongside the benefits.

Blocks production

The two apps need a shared filesystem

They only agree on orders because both resolve the same file path on the same machine. Deployed to separate hosts — the normal arrangement, and the one frontend.md anticipates on Vercel — they would silently stop seeing each other's data. This must be resolved before launch, not after.

Data risk

No write-locking on the order file

Each change rewrites the whole file. A checkout landing at the same instant as an admin status change can lose one of the two. Acceptable for a demo with one tester; not acceptable with real customers.

Future work

There's no API for anything else to call

Server actions are reachable only from these two apps. A mobile app, a partner integration or a delivery-partner webhook would need a real API layer built — work that a plain React app would have forced up front, for better or worse.

Team cost

The server/client boundary must be learned

Knowing which components run where is a genuine skill, and getting it wrong is a common source of build errors. The payoff is the small JavaScript bundle; the cost is onboarding time.

Lock-in

These patterns are Next-specific

Server components and server actions don't transfer to another framework as written. Moving away later means real rework — a reasonable bet given the framework's position, but worth naming.

Contained

The risk sits behind one package

Every one of the above touches only @glowroot/data. All 25 of its data accessors are already asynchronous — written as though they were talking to a database — so swapping the inside for a real one doesn't ripple outward.

The one item that isn't a drop-in

Real sessions are the exception. Today the customer's email is sent from the browser with each request, which proves an account exists but not who is calling. Phase 4 moves identity to a server-held session, and the order-reading and order-placing functions change to read it from there. That's the single place where “swap one package” isn't the whole story — worth planning for rather than discovering.
